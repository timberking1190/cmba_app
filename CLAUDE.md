# CLAUDE.md — cmba_app (CMBA Connect / CMBA+)

Working notes for coding agents. **Read this before building anything.** Written during Phase 0
discovery of the Member Cards initiative (2026-07-02).

## What this app actually is

**Payload CMS 3.85 on Next.js 15.3 (App Router), TypeScript strict, Postgres.** It is *not* a
raw-Supabase / SQL-migrations / Deno-edge-functions app. Identity, data model, access control,
migrations, and admin UI are all Payload.

| Concern | Reality in this repo |
|---|---|
| Framework | Next.js 15.3.9 (App Router, React 19), `type: module` |
| CMS / ORM / admin | Payload 3.85.1 (`payload`, `@payloadcms/*`) |
| Database | Postgres via `@payloadcms/db-postgres` → **Supabase project `pdwautioosstdgbbblxl` ("cmba-connect") in `ca-central-1`** (Montréal). `DATABASE_URL` in `.env`. |
| Auth | **Payload auth** — the `users` collection (`src/collections/Users.ts`) is the auth collection. `req.user` is the identity. There is **no** Supabase `auth.users` / `public.profiles` / `auth.uid()`. MFA (TOTP + passkeys) lives in `MfaTotp`/`WebauthnCredentials`/`RecoveryCodes`. |
| File storage | Supabase Storage (S3-compatible) via `@payloadcms/storage-s3`, `S3_REGION=ca-central-1`. Private buckets for certificate/incident files. |
| Access control | **Payload access functions** in `src/access/` — explicitly "the security boundary for this app (equivalent to RLS)". Default posture is DENY. There is no Postgres RLS. |
| Migrations | Payload migrations in `src/migrations/` (`*.ts` + companion `*.json` snapshot), generated by `npm run migrate:create`. Applied with `npm run migrate`. |
| Email | AWS SES `ca-central-1` (per `DATA_RESIDENCY_AND_COMPLIANCE.md`), sent via `@payloadcms/email-nodemailer`. |
| Hosting | Vercel, functions pinned to Montréal `yul1`. |
| Client state / QR | `qrcode` dep exists but is used **only** for TOTP enrollment today. No wallet/pass code exists yet. |

## Conventions (match these; do not introduce parallel patterns)

- **Data model = Payload collections** (`src/collections/*.ts`), one file per collection, grouped in
  the admin via `admin.group` ("People", "Competition", "Training catalog", …). Field- and
  collection-level access via helpers from `src/access/`. Business logic in collection `hooks`
  (`beforeValidate`/`beforeChange`/`afterChange`).
- **Access helpers** (`src/access/index.ts`): `ROLES`, `hasRole`, `isSuperAdmin`, `isClubAdmin`,
  `isAnyAdmin`, `ownerOrSuperAdmin`, `ownerOrAnyAdmin`, `authenticated`, `superAdminFieldOnly`, etc.
  Returning a Payload `Where` scopes reads instead of all-or-nothing. Per-collection access modules
  live in `src/access/<collection>.ts`.
- **Roles** (the real vocabulary): `participant | coach | official | club_admin | super_admin`.
  Guardians of minors are **not a role** — they are the `guardian` group on the *minor's* `users`
  record, with `isMinor` derived from `dateOfBirth`, guardian-confirmation flow, and consent logging.
- **Server logic** = Next.js Route Handlers under `src/app/(frontend)/api/v1/...` (e.g.
  `api/v1/challenge-submissions/[id]/verify`) using the Payload local API (`req.payload`), and
  reusable libs in `src/lib/`. No Deno, no Supabase Edge Functions.
- **Route groups**: `src/app/(frontend)/` holds role/area routes — `account athlete coach ref rep
  parent guardian guardian-consent compliance manage login score-login schedule standings …`.
  Payload admin lives under `src/app/(payload)/`.
- **Imports pipeline** (the real analog to the spec's "schedule_imports"): the `import-batches`
  collection (`src/collections/ImportBatches.ts`) + `src/lib/csvImport/{parse,validate,commit,lookups}.ts`.
  Pattern: write batch `pending` with a planned manifest → commit rows in bounded chunks recording
  their ids → flip to `committed`; `createdRecords` is the undo manifest; bounded undo window. Specs:
  `cmba-backend-build/docs/CSV_IMPORT_SPEC.md`, `ADMIN_IMPORT_SCREEN_UI.md`.
- **Consent** (`ConsentRecords` + the `users.consents` group): terms/privacy/guardian versions +
  timestamp + IP + granular opt-ins (photo, marketing, recognition surfacing, leaderboard). Logged on
  signup and re-consent.
- **Audit**: `AuditLog` collection + Payload version history; append-only integrity migration exists
  (`20260630_125952_add_audit_integrity`). `IdempotencyKeys`, `RateLimitHits` collections exist for
  those cross-cutting concerns — reuse them.

## Existing credential system (reuse, do not rebuild)

The Member-Cards "three credentials" requirement is **already largely modeled**:

- `CertificationTypes` (`certification-types`) — catalog explicitly built for "NCCP (coaches), RAMP
  (officials), and mandatory compliance (Respect in Sport, **Safe Sport**, concussion, **criminal-record
  check**)". Fields: `category`, `appliesToRoles`, `requiredForRoles`, `isRequired`, `validityMonths`
  (drives auto-expiry), `relatedCourse`. **This is the spec's `card_requirements` matrix** — role →
  required credential is data here, editable without a deploy.
- `Certifications` (`certifications`) — per-user records: `type`, auto-computed `status`
  (pending-verification | valid | expiring | expired) via `src/lib/certStatus`, `issueDate`,
  `expiryDate` (auto-filled from type validity), admin `verifiedBy`/`verifiedAt`, private
  `certificateFile`. Owner-or-super-admin access. **This is the spec's `credentials` table + review
  flow.**
- `CertificateFiles` — private file collection (owner + admin only), short-lived signed URLs. **This
  is the spec's "record-check document transits, never persists" bucket** — but confirm/implement the
  ≤30-day purge (spec D21).
- `Officials`, `GameOfficials`, `Games`, `Venues`, `Seasons`, `Clubs`, `Teams`, `Divisions`,
  `TeamMemberships` — the domain model for who/where/which-game a scan happens against.

## ⚠️ Member Cards spec reconciliation (kickoff prompt vs. this repo)

The Member Cards kickoff prompt assumes a **raw-Supabase stack** (SQL enums, RLS policies,
`private.is_admin()` security-definer fns, `public.profiles`/`auth.uid()`, Deno edge functions in
`supabase/functions/`). **None of that matches this app.** Building it verbatim would create a parallel
architecture and duplicate systems that already exist — which the prompt's own working agreements
forbid. Proposed translation (pending operator confirmation — see the conversation):

| Kickoff-prompt term | Real analog in this repo |
|---|---|
| `public.profiles` / `auth.users` / `auth.uid()` | `users` collection / `req.user` |
| Supabase RLS policies | Payload access functions (`src/access/`) |
| `private.is_admin()` / `is_verification_admin()` / `can_scan()` | role-check helpers in `src/access/` (`isAnyAdmin`, new `canScan`, `isVerificationAdmin`) |
| Deno edge functions (`/verify`, `apple-pass-web`, …) | Next.js Route Handlers under `src/app/(frontend)/api/v1/…` using the Payload local API |
| SQL enums + `create table` migrations | Payload collections → generated migrations (`npm run migrate:create`) |
| `members` person registry | the `users` collection (+ a light `members`/card collection only if dependants without accounts are needed — the guardian/minor model already exists on `users`) |
| `card_requirements` matrix | `certification-types.requiredForRoles` / `isRequired` (already data-driven) |
| `credentials` table | `certifications` collection |
| `credential_reviews` + `credential-review` bucket | `certifications` verify flow + `certificate-files` (add ≤30-day purge) |
| `credential_imports` / `import_field_mappings` / `import_exceptions` | `import-batches` + `src/lib/csvImport` (extend for credential sources + named field mappings) |
| Role vocab `player/referee/parent/volunteer/scorekeeper/commissioner` | `participant/official/(guardian group)/…/super_admin` — **role mapping is an open decision** |
| `league_official` new role (D23) | new value in `ROLES` + `users.roles` options |
| Region migration (D12, "blocking Phase 0.5") | **Already effectively done** — app is on `ca-central-1` (`pdwautioosstdgbbblxl`). Residual: verify/decommission the stale **us-east-2** `cmba_app` project (`vdlpmjmpaalesmddwabo`), which the app does not use. |

**What still needs genuinely new building** (stack-agnostic — these are real): Ed25519 (EdDSA) JWS
pass-token mint + verify; single-active-`jti` revocation model; Apple `.pkpass` generation + PassKit
web-service routes + APNs; Google Wallet class/object; the browser **scanner** PWA (`/scan`); scan
audit log + analytics; scanner device registry; pass claim links. These become Payload collections +
Next.js route handlers, not new-stack components.

## Decisions (locked 2026-07-02 by operator) — see docs/adr/

1. **Build natively on Payload**, not the spec's raw-Supabase/RLS/Deno stack. Reuse existing
   collections; no `supabase/functions|migrations/`. → `docs/adr/0001-member-cards-native-on-payload.md`.
2. **Region already ca-central-1** (`cmba-connect` / `pdwautioosstdgbbblxl`). Phase 0.5 = assert region
   at runtime + verify/decommission the stale us-east-2 `cmba_app` project.
   → `docs/adr/0002-region-already-ca-central-1.md`.
3. **Reuse 5 roles + add `league_official`** (done in `src/access/index.ts`; DB-enum migration is a
   deliberate follow-up). Guardians via the existing guardian/minor model, not a role.
   → `docs/adr/0003-role-model-reuse-plus-league-official.md`.

Phase-1 data-model plan (keep/extend/new per spec table): `docs/member-cards/PHASE1_DATA_MODEL.md`.

### Guardrails learned in discovery
- Do **not** run `npm run migrate:create` / `migrate` against **prod** ad hoc — the DB is ca-central-1
  prod. Generate migrations on a preview/branch DB and apply deliberately.
- Adding a value to a role/enum `select` field needs a generated `ALTER TYPE … ADD VALUE` migration;
  the source-level union change alone is non-breaking until a row uses the value.
- Regenerate `payload-types.ts` (`npm run generate:types`) after collection changes.
